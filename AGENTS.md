# Offer Filter development

- The app shows as "Offer Filter". From 0.4.29 to 0.4.37 it showed as "Dash Buddy"; that name is retired until further notice (DoorDash launched its own "DashBuddy" for Dashers on 30 Sep 2026, and DoorDash polices DASH names). Do not pick names for their closeness to DoorDash, Dasher or "Dash". Only user-visible text carries the name. Keep unchanged: the package com.local.dasherfilter, class and component names, prefs keys, notification channel IDs, the feed files (OfferFilter.apk, latest.json), User-Agents, signing file names, the "Offer Filter Updates" GitHub App and the fixer's own text.

- Stay on main; no branches or worktrees. Stage a complete, tested/versioned change in one commit rather than publishing partially edited main states.
- Network access is for updates, and for problem reports only after the user saves a report token in the app (their explicit opt-in; removing it stops reports and discards unsent ones). Reports go only to this private repository's issues, where the fixer workflow has Claude read them. Every word that is not offer vocabulary is masked before a report leaves the phone. Otherwise offer data, rules, and logs stay on-device unless the user explicitly shares a diagnostic report. Screen text is captured automatically into two on-device rolling logs (offers and status; Dasher's other screens), never older than 24 hours and each about what one report carries; only a report the user shares may carry them, never an automatic report.
- Connecting GitHub in the app (device flow with the user's own GitHub App, a token limited to this repository) is for updates, and for problem reports only after the user also turns on "Send reports through my GitHub connection" (a separate, explicit opt-in; turning it off, turning reports off or disconnecting GitHub stops reports and discards unsent ones). The token goes only to github.com's sign-in endpoints, the GitHub API under this repository's release/ folder, and, with that opt-in, this repository's issues. Connecting never turns reports on by itself. The client ID is public; there is no client secret.
- Place names on the homepage come from Android's own geocoder (the user's choice; Google's servers on most phones): only positions rounded to about half a kilometre are asked about, each once, and names are cached on the phone. Nothing about offers goes with them.
- Tips only open Cash App, Venmo or PayPal at the user's tap, with the author's name from Support.java. The app never charges, counts or sends anything for them.
- Never infer missing pay, travel, or incremental add-on semantics. Unknown is REVIEW, not KEEP or DECLINE. A separate known failure may still decline.
  - The one exception, the user's own rule for one narrow shape, approved in chat ("auto decline but only if the order as a whole including the +$ doesn't meet the min"): a screen offer whose pay is unknown only because one bare "+$X" label sits directly beside its one total "$Y", on a single order (2 stops). The user sees these only while already on a delivery, so they may be add-ons. The offer as a whole, Y + X, is then an upper bound on pay; pay itself stays unknown on every other path. The offer is DECLINED only when even Y + X misses the set rules (the flat minimum, and per mile, minute and stop with the miles, minutes and stops shown; max stops as always). That is the user's choice for this shape, not a proof that every reading fails: if the offer really is an add-on, the add-on rules (the combined route and the added pay) might have let it through. The adaptive floors never count toward this decline (they never judge add-ons). Otherwise the offer is REVIEW, never KEEP. Notifications never use the bound.
- Preserve immediate first decline attempts on a readable foreground offer (the scanner's 150 ms content gap below is the only wait, and it is bounded and logged). Never automatically open Dasher to inspect an unclassified offer. Only the user's tap on one of our cards opens Dasher: through a no-UI activity of ours that starts Dasher's own launch intent (as its launcher icon does, nothing cleared or reset; with Dasher already in one half of a split screen, the plain launch intent brings it forward in that half, and only when our tap screen is itself in one half without Dasher beside it does Dasher open into the other half) and clears that card. Dasher's own notification intent is used only when Dasher has no launch intent. A user's touch during a decline hands that offer back: no further automatic taps on it, even from a read already under way (the touch is checked right before every automatic tap).
- The screen reader looks at windows, reads, decides and taps on its own scanner thread, never on the main thread, which Offer Filter's screen shares. A window change is read at once, and so is any change while the last read showed any sign of an offer or confirmation (pay, a distance, time or stops, an Accept or Decline label, a confirmation, a screen too big to read), a decline is under way or a screen is settling. The one wait: while nothing is up, the first content change after 150 ms of quiet is read at once, and a content change within 150 ms of that read waits until 150 ms after it. So an offer Dasher draws by a content change alone, within 150 ms of a read that found nothing, is first declined up to 150 ms late; the first-step decline line logs what triggered its read and how long the read waited. Do not lengthen that gap or add waits elsewhere. Other threads only read the immutable snapshots the scanner publishes (Dasher on screen, a takeover); the notification path confirms "Dasher on screen" with its own look at the windows, which writes nothing, can only turn on screen into off screen (a look that fails counts as off screen), and asks the scanner to look when they disagree. A touch during a decline is the user's from the moment it lands: the takeover is published before the touch counts as handled. The touch watch goes up ahead of anything queued on the main thread, and a decline's confirmation is not tapped until it is up (or Android refused it, as before). Turning sound down asks again, under the silencer's lock, whether the declined offer is still the newest and the service still running; a next offer's notification puts the sound back at once under the same lock. History lines, the last status, declines learned by hand and our cards are handled on the main thread, in order with the notification path, so a screen reading and a notification of one offer are folded one after the other; views and toasts are touched only on the main thread.
- Sound turned down during a decline is restored exactly (and after a crash). Touch only media and alarm streams, never the ringer/notification/system streams (ringer mode), never during a call, and never over a passing, unknown or next offer.
- Split screen with Dasher happens only at the user's tap (the accessibility split action, then Dasher's own launch intent into the other half). In split screen, Dasher's half is read and may be declined like a foreground window only while the split divider is present and another app's half is the active window; never under the shade, recents or other system surfaces.
- Over Dasher (only while it fills the screen, never over the shade, recents or other system surfaces) the filter tab is the user's to move, at their own drag (the user asked: the immovable tab obscured Dasher's delivery screen): up or down either edge or across to the other (it lands on the nearer edge), kept per orientation, with "Move up", "Move down" and "Move to other side" for screen readers. A drag is never a tap. At rest about half of it is tucked past the edge, still a 48 dp touch target. Over an offer or its confirmation (any sign of one) it is only a slim peek that takes no touches, so it never covers one and every touch there is Dasher's; during a delivery (a stored route or a delivery screen), and on a screen not recognised during a dash, it is that peek until tapped, then out for a few seconds. The best-area guide shows only while Dasher's screen positively shows the wait for offers ("finding offers", the dash's own screen, the dash home) with no route stored: an offer, a delivery or a screen not recognised hides it. It never covers an offer or confirmation and never takes touches. What the tab and guide make of a screen (DasherScene) decides nothing about offers.
- A successful click or PendingIntent send means requested, not server-confirmed. Hiding a notification is not declining an order.
- Notification updates/reconnects must not ring repeatedly. Verify replacement posting/permissions and never remove an original passing/unknown notification merely on an attempted replacement.
- No extra ring when Dasher's own offer alert already sounds (the user's decision): when Android shows that Dasher's own post of the offer sounded, the "Offers to check" card is posted silently instead of ringing. The card stays. From Android 10 that is Android's record of its last audible alert for the notification, at the post (within a second); before Android 10, every condition Android sounds on must hold: the post matches the interruption filter (not held back by Do Not Disturb), Android ranks it at default importance or above, its channel has a sound, and it is neither an only-alert-once update of a notification Android still shows nor a group child that alerts through its summary. A channel's settings alone never count. When in doubt (Android does not say, or any condition fails), the card rings once as before.
- Keep the existing cloud signer. No automatic key generation, key material in source, signing material in public, or independent GitHub signing path.
- The same cloud key may also reach a Claude session as the environment variables OFFER_FILTER_KEYSTORE_B64 and OFFER_FILTER_SIGNING_PASSWORD (set by the user in the environment settings, never in chat, source or GitHub). tools/sign-local.sh is the only way to use it there: it checks the certificate fingerprint, runs the tests, signs, and leaves the APK in dist/. It never publishes. To ship that APK to phones without Render, commit the source, run tools/publish-repo-feed.py (it checks the cloud signer, package, embedded version, a versionCode above the published one, and the feed against the app's own policy code, then writes release/OfferFilter.apk and release/latest.json naming the source commit), commit release/ on its own, and push both commits to main together. Nothing is signed on GitHub.
- Increase versionCode/versionName in app/build.gradle for changed app sources. build-local.sh derives the packaged version from this single source.
- There are two release paths, both carrying only APKs signed with the cloud key: Render (render-build.sh, public/latest.json, public/OfferFilter.apk) for every phone, and release/ on main for phones connected to GitHub. A phone takes the higher versionCode (a tie goes to Render) and still verifies size, SHA-256, package, version and signer. Only tools/publish-repo-feed.py writes release/. Do not publish to the retired old-signer GitHub feed.
- Run testDebugUnitTest (including Robolectric adapters), the signed APK build, and tools/verify_channel.py. Day to day `./gradlew -q testDebugUnitTest` (warm daemon, build cache) simulates Android 15 only; tools/sign-local.sh, the fixer's gate, Render and CI pass `-PallSdks` so every release is tested on Android 8 and 15. Bump the version before the final test run so signing reuses that result. The probe uses actual production UpdateTransport, exact size/SHA, APK package/version, and signer verification. Report which live version it tested.
- The offer-report fixer (.github/workflows/offer-report-fix*.yml, tools/fixer/) ships only through its gate and Render: one commit touching app code, tests, version lines and notes (never the updater); tests that compile and fail on the old code; full tests, lint and packaging. Claude and the gate get read-only tokens; only the ship job writes, and it runs no code from the fix. Never let the fixer edit workflows, tools/, build, signing or release files, give Claude a write token, or weaken the gate.
- Final release checks must distinguish Java/unit tests, simulated Android adapter tests, published APK verification, real handset installation, and real DoorDash audio/haptic behavior. Do not conflate them.
