# Offer Filter development

- The app shows as "Offer Filter". From 0.4.29 to 0.4.37 it showed as "Dash Buddy"; that name is retired until further notice (DoorDash launched its own "DashBuddy" for Dashers on 30 Sep 2026, and DoorDash polices DASH names). Do not pick names for their closeness to DoorDash, Dasher or "Dash". Only user-visible text carries the name. Keep unchanged: the package com.local.dasherfilter, class and component names, prefs keys, notification channel IDs, the feed files (OfferFilter.apk, latest.json), User-Agents, signing file names, the "Offer Filter Updates" GitHub App and the fixer's own text.

- Stage a complete, tested/versioned change in one commit rather than publishing partially edited main states.
- Network access is for updates, and for problem reports only after the user saves a report token in the app (their explicit opt-in; removing it stops reports and discards unsent ones). Reports go only to this private repository's issues, where the fixer workflow has Claude read them. Every word that is not offer vocabulary is masked before a problem report leaves the phone. Otherwise offer data, rules, and logs stay on-device unless the user explicitly shares a diagnostic report, or turns on diagnostics after each dash (below).
- Screen text is masked at capture (the user's decision, approved in chat: "can we get automatic report sharing"). PersonalText masks every label before it is written to either on-device log, the decision history's read lines or any report: a customer's name after "Deliver to", "Delivery for", "Drop off for", "Order for" or "Customer:" and in "Sam's order", the dasher's own name above "N orders completed", street addresses, city/state/ZIP lines and Apt/Suite values, phone numbers, emails, and a customer's own drop-off words (quoted, or after "Leave at my door:" and like headings) become [name], [address], [phone], [email] and [instructions]. Store and business names, offer words, money, miles, minutes, stops, times, buttons and shopping items stay. Masking is deterministic, and masked text masks to itself. Offer reading and decisions always use the raw labels; only what is stored or sent is masked. Log lines are built and masked on the log's writer thread from copies (never on the screen reader's thread); a history line's few read lines are masked as the line is made, after any Decline tap. Screen text is captured automatically into two on-device rolling logs (offers and status; Dasher's other screens), never older than 24 hours and each about what one report carries. Turn-by-turn navigation (a label "mph" and one with a distance in ft or mi) goes into the screens log as "[navigation]" lines at most once a minute whatever its words, on a budget of its own, so it never holds back another screen; when the screens log, or a report's share of it, is full, navigation lines and lines older than 30 minutes go first, oldest first, so navigation never pushes another screen of the last 30 minutes out (the pickup leg after an Accept, which 0.4.41's navigation pushed out of the user's report). Only a report the user shares, or the diagnostics after a dash that the user turned on, may carry them (masked), and those diagnostics go only to this private repository's issues. A problem report never carries the logs.
- Connecting GitHub in the app (device flow with the user's own GitHub App, a token limited to this repository) is for updates, and for problem reports only after the user also turns on "Send reports through my GitHub connection" (a separate, explicit opt-in; turning it off, turning reports off or disconnecting GitHub stops reports and discards unsent ones; a connection that ends by itself, because GitHub refused to renew it or its renewal ran out, counts as disconnecting). Why a connection ended is logged and kept for the shared report, never a token, the account name or a code. One token renewal runs at a time, and the stored connection is never locked while GitHub answers. The token goes only to github.com's sign-in endpoints, the GitHub API under this repository's release/ folder, and, with that opt-in, this repository's issues (and comments on them). Diagnostics after each dash ("Share diagnostics after each dash" under Reports, off by default) are a further explicit opt-in: the switch can be on only while GitHub is connected and "Send reports through my GitHub connection" is on, and anything that turns that off (turning it off, turning reports off, disconnecting, a connection that ends by itself) also turns the switch off and discards unsent diagnostics, as does turning the switch off; connecting again never turns it back on. With it on, once a dash ends (Dasher's dash-over screen: the dash ended, its summary or the "Dash now" home, not a pause; Dasher's "End dash" screen when it shows nothing else of the dash; or 30 minutes with no offer after the last one), the report Share report builds, masked and whole, is filed as one issue titled "[diagnostics] Offer Filter <version> <start>–<end>" with the label diagnostics, split into the issue body and comments of at most 60,000 characters each. A dash runs from its first offer after the last one filed; at most one issue per dash and six a day. It goes only through the GitHub connection's own token (never a pasted one), only to this repository's issues; the outbox retries it with backoff when offline, keeps the issue's number once filed so a retry only sends the comments still owed, and never logs or includes the token. The fixer never acts on diagnostics issues. Connecting never turns reports on by itself, and neither does connecting again: a stored connection that Connect GitHub replaces (also one that ended by itself before the app noticed) counts as disconnecting, and a new connection starts with reports through it off. The client ID is public; there is no client secret.
- Place names on the homepage come from Android's own geocoder (the user's choice; Google's servers on most phones): only positions rounded to about half a kilometre are asked about, each once, and names are cached on the phone. Nothing about offers goes with them.
- Tips only open Cash App, Venmo or PayPal at the user's tap, with the author's name from Support.java. The app never charges, counts or sends anything for them.
- Never infer missing pay, travel, or incremental add-on semantics. Unknown is REVIEW, not KEEP or DECLINE. A separate known failure may still decline.
- Score by area is a user-chosen rule mode (off by default; strict stays the default): a standalone offer passes at an area score of 100% or more (AreaScore: the polygon of pay ÷ each active spoke's floor, over the spokes in their drawn order, against the minimums' polygon; with the adaptive minimum on a floor is the higher of the set minimum and what the strict rules' adaptive floor asks of that offer), declines below. Pure area, no per-spoke floor (the user's decision): only max stops stays a hard limit. Pay or an active spoke's amount unread is REVIEW, never a score from what is missing. A "+$X" ceiling declines only when even Y + X scores under 100% on the set minimums alone, else REVIEW. Add-ons always keep the strict rules. The score is shown (ticket, history, reports, screen readers) in either mode, and is never a decision in strict mode.
  - The one exception, the user's own rule for one narrow shape, approved in chat ("auto decline but only if the order as a whole including the +$ doesn't meet the min"): a screen offer whose pay is unknown only because one bare "+$X" label sits directly beside its one total "$Y", on a single order (2 stops). "Directly beside" allows only offer chrome between the two labels: the offer's own Decline or Accept control, a countdown ("0:35") or the short busy badge ("Very busy", "Busy"), as Dasher really draws it ("Very busy, +$1, Decline, $5.75"); any other label between them keeps them apart. The user sees these only while already on a delivery, so they may be add-ons. The offer as a whole, Y + X, is then an upper bound on pay; pay itself stays unknown on every other path. The offer is DECLINED only when even Y + X misses the set rules (the flat minimum, and per mile, minute and stop with the miles, minutes and stops shown; max stops as always). That is the user's choice for this shape, not a proof that every reading fails: if the offer really is an add-on, the add-on rules (the combined route and the added pay) might have let it through. The adaptive floors never count toward this decline (they never judge add-ons). Otherwise the offer is REVIEW, never KEEP. Notifications never use the bound.
- Learning from what the user does with an offer (the user's decision, approved in chat: fix the accept and decline detection, "including counting an acceptance without a tap"). A wrong lesson raises the minimums until Reset and declines good offers, so whenever the evidence is ambiguous nothing is learned and the history says why. An offer counts as ACCEPTED on a seen Accept tap followed by a delivery screen, or, with no tap seen, only when all of these hold: it is a readable standalone offer the app did not decline (KEEP, or REVIEW left to the user); Dasher's wait for offers was read after the offer before it and before it came (positive evidence the user was waiting: unknown, a restart, another offer or an unclear screen since, or a stored route, is not); it closed while its countdown still had more than 3 s left (the countdown at its last read, less the time until a read found it gone); Dasher never asked to confirm declining it, no Decline tap on it was seen and no decline of it was requested (on screen or through Dasher's notification); and within 60 s Dasher's next settled non-offer screen is a delivery or route screen (AcceptedOfferTracker's progress labels, DasherScene's route markers, among them the drop-off leg as the user's 0.4.41 report captured it: labels beginning "Deliver to " or "Arriving at", and "Leave it at the door", "Hand it to me", "Verify correct order", "Check you have the correct order from pick-up", "Take photo of drop-off location", "Handed order to customer", "Confirm you handed order directly to customer", "Confirm to complete delivery", "Arriving soon", "Remember to grab the drinks before delivering the order", case-insensitive), not the wait for offers (which includes, from the same report, the dash's summary between deliveries, "This dash so far" and "Continue dashing", and the zone screens, "Dash here", "Navigate back to old zone" and "Switch to this zone with peak pay!") or the dash's end. Turn-by-turn navigation alone ("mph" and a distance, "Turn left", "Exit") is neither: it shows on the way to a customer and back to a zone alike, so with no other marker it is unclear. Dasher's "End your current dash?" is unclear, whatever it is drawn over; it counts as the dash's end only once the user's "End dash" on it was seen (a click naming exactly "End dash" and not "Go back") and a read after it shows neither the question nor the dash (no delivery, no wait for offers, no offer); a screen of the dash means it went on. A seen Accept tap on a standalone offer still teaches nothing when a delivery was under way as it came (a stored route, or the last delivery-or-waiting screen read was a delivery) or its countdown, when read, had 3 s or less left as it went. A next screen that is neither (settled: its words unchanged 5 s; an empty screen, or one replaced sooner, is passed over), or that shows a delivery and the wait for offers at once, teaches nothing and goes to the screens log; a read showing any of an offer's facts (pay, miles, minutes, stops) is an offer being drawn, never a next screen, except figures the screen explains itself: navigation's distances and times (pay or stops on it still count), and every figure on the dash's summary ("This offer $9.00"). That exception is the learning classifier's only: what the screen reader reads at once, the tab and the guide still take any distance or time as a sign of an offer. Add-ons count only with a seen tap; unread pay never teaches. An acceptance is learned once (the tap path and what came after the offer never both). The wait for offers, the dash's end or Dasher's home with its Dash button, with no delivery marker on the same screen, ends a stored route. An offer counts as DECLINED BY HAND on a seen Decline tap, or when Dasher's own "Are you sure you want to decline this offer?" appears for an offer the app left alone with no decline of the app's own (or of the notification path) under way and no tap of the app's within 5 s. Either is held, and counts only when Dasher next shows the wait for offers, or another offer comes with no other screen read between (a seen tap also when Dasher goes back to a delivery that was under way before). It counts nothing on going back to the offer (any read of it after the question or tap, unless the wait for offers or the next offer follows at once), a later Accept tap on it, a delivery screen (for the question alone, or with none under way before), an unclear screen that settles, the minute running out, or the dash ending (or Dasher's home with its Dash button). The app never answers that question. Labels below a tapped node name it only when they are few (6 at most) and show none of an offer's facts, so a tap on an offer card's body is no Accept; the last offer's Accept and Decline controls name only a click made before a read found that offer gone. Dasher's "New Delivery!" / "New Order: Go to …" (notification or screen) is a new offer, never acceptance evidence; the card may name its store. A click on the node of a tap of the app's that Android took (within 5 s after the tap began), or a click with no node whose own time (not when its event arrived) lies in one of the app's taps' echo windows, is the app's own; any other click is the user's; the notification path marks its Decline before sending it. Each step (accepted by tap or by close, declined by hand, not learned and why) is a learning line under the offer in the decision history: it never changes the offer's action, tally or totals, and never goes into an automatic problem report (the shared report carries them, and so do the diagnostics after a dash, which are that report). Never widen this evidence with guessed wording: beyond the delivery, pickup and directions markers the decision names, new delivery or waiting wording comes only from screens a report captured.
- Preserve immediate first decline attempts on a readable foreground offer (the scanner's 150 ms content gap below is the only wait, and it is bounded and logged). Never automatically open Dasher to inspect an unclassified offer. Only the user's tap on one of our cards opens Dasher: through a no-UI activity of ours that starts Dasher's own launch intent (as its launcher icon does, nothing cleared or reset; with Dasher already in one half of a split screen, the plain launch intent brings it forward in that half, and only when our tap screen is itself in one half without Dasher beside it does Dasher open into the other half) and clears that card. Dasher's own notification intent is used only when Dasher has no launch intent. A user's touch during a decline hands that offer back, and so does any click of theirs on Dasher during it ("View offer details", "Go back", "Cancel", the offer card, any control) and going back to the offer from its question (the same offer showing again after its screen gave way to its question, or to any screen without its Accept and facts, with no tap on the question's Decline taken; the user's 0.4.42 report: Decline tapped, "Decline offer" not, "View offer details", the same offer declined again). Handed back means no further automatic taps on it, even from a read already under way (touches and clicks are checked right before every automatic tap), the sound restored, the takeover toast, status and history action (USER_TOOK_OVER); it lasts until a clearly different offer, Dasher idle or on a delivery, or 2 minutes. Each of the app's taps (each performAction call; none for a control found not clickable, where nothing is asked of Android) has its own echo window, from the call until 150 ms after it returns; no later tap and no read extends it. A touch the watch reports inside one (by the touch's own time) is that tap's echo (Android can report the app's own action as a touch outside the watch; both 0.4.41 declines did): it is ignored. A click event is the app's own only when it is on the node of a tap that Android took or that was under way, within 5 s after that tap began, or, with no node, when its own time lies in a tap's echo window; a click on any other node is the user's however soon after a tap of the app's, and wins over a touch judged an echo. Clicks are judged on the main thread from what the event already holds (node identity and time, no call into Dasher). Logged: "touch ignored: own-action echo", "touch during decline: the user's", "your tap on Dasher", "you went back to the offer from Dasher's question", each with the time since the app's tap. Dasher's question is tried 3 times at most (the first try and two retries, 300 ms apart, each with a read of its own; refused by Android, or taken and not acted on by Dasher); then "confirmation not tapped" is logged and the offer is left to the user as a takeover. Once the declined offer's screen gave way, its first Decline is never tapped again, with one exception: Dasher closed the question the app confirmed, nothing of the user's was seen, and the offer is still showing 2 s later (logged as a Dasher glitch): one more first Decline per decline; a second time is given up. A decline's episode ends at the wait for offers (or the dash's end), a delivery, a clearly different offer, the hand-back, or 2 minutes after its first tap; the same offer after that is a new offer. Every look for the question while it is awaited (which window, found or why not) and every try (requested, refused and why, skipped and why) is logged, with repeats counted rather than repeated.
- The screen reader looks at windows, reads, decides and taps on its own scanner thread, never on the main thread, which Offer Filter's screen shares. A window change is read at once, and so is any change while the last read showed any sign of an offer or confirmation (pay, a distance, time or stops, an Accept or Decline label, a confirmation, a screen too big to read), a decline is under way or a screen is settling. The one wait: while nothing is up, the first content change after 150 ms of quiet is read at once, and a content change within 150 ms of that read waits until 150 ms after it. So an offer Dasher draws by a content change alone, within 150 ms of a read that found nothing, is first declined up to 150 ms late; the first-step decline line logs what triggered its read and how long the read waited. Do not lengthen that gap or add waits elsewhere. Offer reads first: every node fetched is a call Dasher's own UI thread must serve, and it is busiest exactly while an offer animates in. A window change, and any event of Dasher's while an offer or confirmation is up, a decline is under way, or one was seen in the last 3 s, is handed to the front of the scanner's queue (a second such read in a row goes behind what is due, so Android's news of the ring and the timers still run). What is not essential (the window watch, reading around a click, settling and capturing what came after an offer) does not run while an offer or confirmation is up or a decline is under way (the window watch then only asks Android for its list of windows, never Dasher, and reads at once when it changed), runs only after the read Dasher's events asked for, and stops at its next call into Dasher when Dasher sends another event; a click while an offer is up is named only by what its event says and by the last offer read's own controls. After the first Decline tap, Dasher's question is looked for every 100 ms for 3 s instead of re-reading every 200 ms: a poll asks Android for the windows and reads only when they, or Dasher's events, changed since the last read; a read never reads the same window twice and reads Dasher's other windows (the newest first, two at most, 200 nodes each) only when the window just read does not ask the question (also when a poll's read of the window just read stops at its 200 nodes: 0.4.42 looked nowhere else then); and while the question is awaited, a read of the offer stops at a window change (twice in a row at most) so the question's window is read at once. The confirmation is tapped the moment it is found, still only when it belongs to the declined offer; the log gives the time from the first Decline tap to the question found and tapped. Every read slower than 150 ms while an offer or confirmation is (or was just) up or a decline is under way is logged, with where its time went (windows, root, traversal, nodes); idle ones once a minute. Other threads only read the immutable snapshots the scanner publishes (Dasher on screen, a takeover); the notification path confirms "Dasher on screen" with its own look at the windows, which writes nothing, can only turn on screen into off screen (a look that fails counts as off screen), and asks the scanner to look when they disagree. A touch during a decline is the user's from the moment it lands: the takeover is published before the touch counts as handled. The touch watch goes up ahead of anything queued on the main thread, and a decline's confirmation waits for it at most 50 ms after it was asked for (or not at all if Android refused it, as before), then is tapped all the same: the touch is still checked right before the tap. Turning sound down asks again, under the silencer's lock, whether the declined offer is still the newest and the service still running; a next offer's notification puts the sound back at once under the same lock. History lines (and the learning lines under them), the last status, declines learned by hand and our cards are handled on the main thread, in order with the notification path, so a screen reading and a notification of one offer are folded one after the other; views and toasts are touched only on the main thread.
- Sound turned down during a decline is restored exactly (and after a crash). Touch only media and alarm streams, never the ringer/notification/system streams (ringer mode), never during a call, and never over a passing, unknown or next offer.
- Split screen with Dasher happens only at the user's tap (the accessibility split action, then Dasher's own launch intent into the other half). In split screen, Dasher's half is read and may be declined like a foreground window only while the split divider is present and another app's half is the active window; never under the shade, recents or other system surfaces.
- Over Dasher (only while it fills the screen, never over the shade, recents or other system surfaces) the filter tab is the user's to move, at their own drag (the user asked: the immovable tab obscured Dasher's delivery screen): up or down either edge or across to the other (it lands on the nearer edge), kept per orientation, with "Move up", "Move down" and "Move to other side" for screen readers. A drag is never a tap. At rest about half of it is tucked past the edge, still a 48 dp touch target. Over an offer or its confirmation (any sign of one) it is only a slim peek that takes no touches, so it never covers one and every touch there is Dasher's; during a delivery (a stored route or a delivery screen), and on a screen not recognised during a dash, it is that peek until tapped, then out for a few seconds. The best-area guide shows only while Dasher's screen positively shows the wait for offers ("finding offers", the dash's own screen, the dash home, the dash's summary between deliveries, the zone screens), not Dasher's "End your current dash?", with no route stored: an offer, a delivery or a screen not recognised hides it. It never covers an offer or confirmation and never takes touches. What the tab and guide make of a screen (DasherScene) decides nothing about offers.
- A successful click or PendingIntent send means requested, not server-confirmed. Hiding a notification is not declining an order.
- Notification updates/reconnects must not ring repeatedly. Verify replacement posting/permissions and never remove an original passing/unknown notification merely on an attempted replacement.
- No extra ring when Dasher's own offer alert already sounds (the user's decision): when Android shows that Dasher's own post of the offer sounded, the "Offers to check" card is posted silently instead of ringing. The card stays. From Android 10 that is Android's record of its last audible alert for the notification, at the post (within a second); before Android 10, every condition Android sounds on must hold: the post matches the interruption filter (not held back by Do Not Disturb), Android ranks it at default importance or above, its channel has a sound, and it is neither an only-alert-once update of a notification Android still shows nor a group child that alerts through its summary. A channel's settings alone never count. When in doubt (Android does not say, or any condition fails), the card rings once as before.
- Keep the existing cloud signer. No automatic key generation, key material in source, signing material in public, or independent GitHub signing path.
- The same cloud key may also reach a Claude session as the environment variables OFFER_FILTER_KEYSTORE_B64 and OFFER_FILTER_SIGNING_PASSWORD (set by the user in the environment settings, never in chat, source or GitHub). tools/sign-local.sh is the only way to use it there: it checks the certificate fingerprint, runs the tests, signs, and leaves the APK in dist/. It never publishes. To ship that APK to phones without Render, commit the source, run tools/publish-repo-feed.py (it checks the cloud signer, package, embedded version, a versionCode above the published one, and the feed against the app's own policy code, then writes release/OfferFilter.apk and release/latest.json naming the source commit), commit release/ on its own, and push both commits to main together. Nothing is signed on GitHub.
- Update checks: opening the app, turning updates on, the retry job and the user's own check start at once (after the cooldown or failure backoff); coming back to the app, a recreation, a service reconnecting and the periodic job wait 5 minutes after the last attempt. An automatic check logs its result only when it changes (or daily); failures, manual checks and install steps always log. DoorDash's channel and extra-key lines are logged once per change per channel. Never weaken update verification for any of this.
- Increase versionCode/versionName in app/build.gradle for changed app sources. build-local.sh derives the packaged version from this single source.
- There are two release paths, both carrying only APKs signed with the cloud key: Render (render-build.sh, public/latest.json, public/OfferFilter.apk) for every phone, and release/ on main for phones connected to GitHub. A phone takes the higher versionCode (a tie goes to Render) and still verifies size, SHA-256, package, version and signer. Only tools/publish-repo-feed.py writes release/. Do not publish to the retired old-signer GitHub feed.
- Run testDebugUnitTest (including Robolectric adapters), the signed APK build, and tools/verify_channel.py. Day to day `./gradlew -q testDebugUnitTest` (warm daemon, build cache) simulates Android 15 only; tools/sign-local.sh, the fixer's gate, Render and CI pass `-PallSdks` so every release is tested on Android 8 and 15. Bump the version before the final test run so signing reuses that result. The probe uses actual production UpdateTransport, exact size/SHA, APK package/version, and signer verification. Report which live version it tested.
- The offer-report fixer (.github/workflows/offer-report-fix*.yml, tools/fixer/) ships only through its gate and Render: one commit touching app code, tests, version lines and notes (never the updater); tests that compile and fail on the old code; full tests, lint and packaging. Claude and the gate get read-only tokens; only the ship job writes, and it runs no code from the fix. Never let the fixer edit workflows, tools/, build, signing or release files, give Claude a write token, or weaken the gate. It acts only on issues titled "[offer-report]…", never on "[diagnostics]" issues, and is opt-in until its Android SDK setup is repaired: it runs only while the repository variable OFFER_FIXER_ENABLED is true.
- Final release checks must distinguish Java/unit tests, simulated Android adapter tests, published APK verification, real handset installation, and real DoorDash audio/haptic behavior. Do not conflate them.
