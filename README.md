# Offer Filter

A local Android assistant for reviewing and declining DoorDash delivery offers. Not made by or affiliated with DoorDash. Read [Risks](#risks) before using it. From 0.4.29 to 0.4.37 it showed as "Dash Buddy"; that name is retired. The package (com.local.dasherfilter) and signer never changed, so every version updates over the last. Android 8+; release build targets Android 15.

## Risks

- **DoorDash's terms and your account.** Using a third-party tool with the Dasher app may break DoorDash's terms, and DoorDash could limit or deactivate your account. Declining offers can also lower your acceptance rate.
- **Not affiliated with DoorDash.** Offer Filter is independent software. DoorDash and Dasher are trademarks of DoorDash, Inc., named only to say which app it works with.
- **It can be wrong, and there is no warranty.** It can misread an offer, decline one you wanted or fail to decline one; a tap is only a request to Dasher. Check your Dasher history. It is provided as is, without warranty ([TERMS.md](TERMS.md), [LICENSE](LICENSE)).
- **Not while driving.** Don't handle your phone while driving: set your rules before you drive and pull over to look at offers. It is not a safety device.
- **Your data.** What it reads, keeps and sends, and when, is in [PRIVACY.md](PRIVACY.md).

The three texts are drafts, not legal advice: have a lawyer review them before any public release.

## What it actually does

When a real offer screen is visible in Dasher, Accessibility reads the displayed payout, mileage, duration and stop count. A known enabled-rule failure can request Decline immediately and handle the subsequent confirmation. This is a UI request, not proof of server acceptance.

Reading never holds up Offer Filter's own screen. Each read asks Android for the windows and walks up to 1,500 of Dasher's screen elements, every one a call into Dasher (0.2 to 0.7 seconds a read on a slow phone), and Dasher sends many events a second while its map or countdown moves. All of that (every look at the windows, every read, every tap, the confirmation, the touch takeover and the sound) runs on the screen reader's own thread; the main thread, which Offer Filter's screen uses, only notes each event and hands it over, and a read already queued is not queued again. A window change is read at once, and so is every change while the last read showed any sign of an offer (pay, a distance, Accept or Decline, a confirmation), a decline is under way, or a screen is still settling. While nothing is up, the first content change after 150 ms of quiet is read at once too; the changes that follow within 150 ms of that read (the map redrawing, a clock ticking) are read together, once, 150 ms after it. So an offer that opens as a new screen, or that the last read already saw part of, is declined at once, while an offer Dasher draws by a content change alone, within 150 ms of a read that found nothing, is declined up to 150 ms later than it could be. Each first Decline line in the diagnostic log says what started its read and how long that read waited. The history, the last status, declines learned by hand and Offer Filter's cards are handled on the main thread in order with Dasher's notifications, so a screen reading and a notification of the same offer are still one line with no card left behind.

Offer reads come first. Every element read is a call Dasher's own screen thread has to answer, and that thread is busiest exactly while an offer slides in, so nothing that can wait gets in an offer's way. A window change, and any of Dasher's events while an offer or its confirmation is up, a decline is under way, or one was seen in the last 3 seconds, is read ahead of anything else waiting. The work that can wait (the half-second check that Dasher is still on screen, reading around a tap, noting what came after an offer) does not run while an offer or confirmation is up or a decline is under way, runs only after the read Dasher's events asked for, and stops at its next call into Dasher when Dasher sends another event. While an offer is up, a tap on Dasher's screen is named only by what Android says about it and by the offer's own Accept and Decline buttons that the read found, without reading around it. After the first Decline tap, Dasher's "Are you sure?" is looked for every 100 ms for 3 seconds: Android's list of windows is checked (that asks Android, not Dasher), and the screen is read only when it, or Dasher's events, changed; no read looks at the same window twice, and while the question is awaited, a read of the offer stops when a new window opens, so the question's own window is read at once. It is tapped the moment it is found, and the diagnostic log says how long after the first tap it was found and tapped. Every read slower than 150 ms while an offer or confirmation is (or was just) up or a decline is under way is noted in the diagnostic log, with where the time went (listing the windows, fetching the screen's root, walking its elements, and how many); slow reads while nothing is up are noted once a minute at most. So a shared report shows the phone's real timings.

The confirmation step belongs only to the offer that was declined. A confirmation needs a prompt ("Are you sure…", "Decline offer?") or a way back ("Cancel", "Go back"); a lone Decline button is how a new offer looks while it is still being drawn. A screen whose pay, distance, time or stops contradict the declined offer is a different offer and is judged on its own. Once the tapped confirmation closes, the authority ends.

In the background, a notification containing sufficient explicit offer data can be evaluated. Passing offers receive a selective Offer Filter alert. An offer that cannot be judged gets a card on **Offers to check** that rings once while Dasher is in the background, so it is not missed. The card names the store Dasher's notification names ("Taco Bell offer: open Dasher to check it"), or says "DoorDash offer" when it names none. Dasher's "New Delivery!" / "New Order: Go to …" is a new offer, never a sign that you accepted one. When Android shows that Dasher's own notification of that offer sounded, the card comes without a ring of its own; it stays all the same. Once the screen has read that offer (whatever it decided, and whether or not the card rang), its card is cleared, including when you come back to the same offer later, and it does not come back when Android reconnects the notification listener; a card for an offer the screen never read stays, also when you pause, resume or change the rules. Dasher's notification of an offer the screen read moments before gets no card at all. Dasher's own notification is never touched for either. Tapping a card opens Dasher the way its launcher icon does, so Dasher comes forward with the offer it is showing (nothing in it is reset), in its own half when it is already beside Offer Filter in split screen (or into the other half when the screen is split without Dasher), and the card goes. The tap goes through a screen of Offer Filter's that never shows, because Android 12 and later let a notification tap start an app's screen only directly, not through a service or broadcast. Cards used to open Dasher's own notification intent, which on some phones opened a screen that could not find the offer; it is still used if Dasher has no launcher entry to open. This happens only at your tap: the app never opens or foregrounds Dasher by itself. A background notification with only a merchant name cannot establish payout, distance, or whether the order passes.

If a known-failing background offer exposes a DoorDash-owned Decline action that opens no screen, the app can request it. Otherwise it can hide the notification only. **Hiding a notification does not decline the order**; it may remain pending until acted on or expired.

## Sound, vibration and missed-offer tradeoffs

Keep DoorDash notifications allowed and set its offer channel to Silent. Offer Filter cannot change another app's notification settings.

Dasher also rings and vibrates for an offer with its own sound, outside its notifications, until the offer closes. **Mute Dasher's ring while declining** (Settings; on by default) turns down the media and alarm streams while a filtered offer is being declined on screen.

- **What it touches.** Only the media and alarm streams, only while that declined offer or its own confirmation is showing, and only when something other than navigation or a call is playing on them.
  - The alarm stream can't be muted, so it goes to its lowest level instead.
  - The ringer, notification and system streams are never touched, because muting them switches the whole phone to vibrate.
- **When it gives way.** Nothing is touched while a call rings or is in progress, and a call that starts mid-decline brings everything back at once. A next offer on screen, a new offer notification, or a passing offer's bell does the same.
- **Restoring.** Everything comes back when the decline ends, after 20 seconds at most, or at the next start if the app died in between.

Navigation voice shares the media stream, so if Dasher's ring plays there, directions are quiet for those seconds too. If Dasher rings on the ringer or notification stream, this setting can't help. The decision's diagnostics log which stream was playing. Android gives an app no way to stop another app's vibration, so the buzz lasts until Dasher closes the declined offer. Declines that don't finish within 5 seconds are reported.

Touching the screen while a decline is in progress hands the offer back, and so does any tap of yours on Dasher during it ("View offer details", "Go back", "Cancel", the offer card, any button) and going back to the offer from Dasher's question. Going back counts even when Android reports neither your touch nor your tap: the same offer showing again after its question, with no tap on the question's Decline taken, is yours. The confirmation is not tapped, that offer is not declined again (from the screen or its notification), the sound comes back, and a toast says so. The touch or tap counts from the moment it lands: it is checked right before every automatic tap, so even a read already under way taps nothing more on that offer. The takeover holds through partly drawn frames of that offer. It ends when Dasher goes idle or to a delivery, when a clearly different offer appears, or after two minutes. A tiny invisible accessibility overlay notices the touch without receiving it. The app's own taps are accessibility actions, not touches, but Android can report one to that overlay as a touch: a touch during one of the app's taps or within 150 ms after it is that echo, and it is ignored. Each tap has a window of its own, which no later tap or read extends. A tap Dasher reports on any button the app did not tap is always yours, even inside such a window; only a tap on the very button the app tapped (or, when Android names no button, one timed inside an app tap's window) is the app's own. Each kind is noted in the diagnostic log with the time since the app's tap. In split screen (your decision), only a touch on Dasher's half hands the offer back: touching Offer Filter's own half (to look at the map or the constellation) lets the decline go on. Offer Filter's page knows its own touches, and Android tells it and the overlay of the same touch in either order, so for up to a tenth of a second nothing is tapped on that offer while the touch is matched; a touch the page never heard of is yours, on Dasher's half. Android does not say where a touch landed in another app's window, so with another app in the other half a touch there still hands the offer back. With Dasher full screen, or when Android gives no bounds for Dasher's half, every touch counts as before, and a tap Dasher reports is always on Dasher's half. The overlay goes up first thing on the main thread; the confirmation waits for it at most 50 ms after the first Decline tap, then is tapped all the same (a touch is still checked right before the tap). A decline whose confirmation was already tapped can't be undone.

Dasher's question ("Are you sure you want to decline this offer?") is tried three times at most: when Android refuses the tap, or takes it and Dasher still asks, it is tried again 300 ms later, twice. Then the log says "confirmation not tapped", a toast says Offer Filter couldn't confirm the decline, and the offer is left to you. Once the question has shown, that offer's first Decline is never tapped again. The one exception: Dasher closed a question Offer Filter confirmed, nothing of yours was seen, and the offer still shows two seconds later. That is logged as a Dasher glitch and gets one more Decline; a second time, the offer is left to you. The diagnostic log has a line for every look at the question while it is awaited (where it looked, found or why not) and every try (taken, refused and why, or skipped and why). A channel's name does not establish its actual configuration; opt-in diagnostics record actual channel sound, vibration, importance, and presence of a full-screen intent when Android exposes these.

Two alerts can ring, each at most once per offer and only while Dasher is not on screen. Whether Dasher is on screen is what the screen reader last saw, at every read and every half second while Dasher is on screen. Dasher sends no event when another app comes in front of it, so while that says Dasher is on screen, a notification checks Android's windows again itself: one that comes just after you leave Dasher still rings (a check that fails counts as Dasher gone). A proven passing offer rings on **Offers that pass**. An offer that cannot be judged rings on **Offers to check**: DoorDash's background notification shows no pay, or auto-decline is paused. It stays silent only when Android shows that Dasher's own post of the offer sounded: from Android 10, Android's record that it last alerted audibly for it at that post; before Android 10, a post that Do Not Disturb let through, at default importance or above, on a channel with a sound, and neither an only-alert-once update nor a group child that alerts through its summary. Then Dasher's alert is the one heard; otherwise (Do Not Disturb, a demoted post, an only-alert-once update, or Android not saying) it rings once. Nothing rings on a replay, a reconnect, or for a known failure. An update of an offer the screen has not read rings only if its first card was silent because Dasher was on screen and Dasher has since left, since it may then be a next offer; while Dasher is on screen, an update of an offer the screen already read adds no card. DoorDash reuses one notification for a store's offers: a re-post with the same text is a new offer once the screen saw the last one end (Dasher idle, a delivery, or the dash over), or, with Dasher off screen, when it comes more than 15 seconds after the last post (an update of an old offer that came that way would be announced as a new one). With Dasher off screen, a re-post with changed text after the screen read the last offer and cleared its card is a new offer too, and may ring once; an unchanged re-post moments later, or a replay, never rings. A same-store re-post while Dasher is on screen, after the screen saw the last offer end, is the notification of the offer on screen: it does not stop that offer's decline (its "Are you sure?" is still tapped). Each such re-post is logged. An offer that could not be judged is never declined or opened automatically; the alert only says to look. Before 0.4.16 these offers got a silent card, and with DoorDash's own offer channel silenced, background offers went unnoticed.

The app retains original passing/unknown notifications rather than deleting them merely because it tried to post a replacement. Alert permission denial, blocked channels, reconnects, duplicate updates, expiration, and stale removals are handled separately.

## Rules and add-ons

Stops count pickups plus drop-offs, as DoorDash shows them: a single order is 2 stops and a double is 4. A "(N stops)" breakdown beside pickups or drop-offs is not the total. Zero disables a rule. Required pay is `max(flat, miles × per-mile rate, minutes × per-minute rate, stops × per-stop rate)`: per stop is a minimum like per mile and per minute, not a fee added on top. Maximum stops is inclusive. The extra-stop fee of earlier versions (added for each stop after two) meant something else, so it is not carried over: updating removes it and leaves per stop off, and the diagnostic log notes the fee that was retired.

The optional **Adaptive minimum** rises with the standalone offers you accept, and with ones you decline by hand:

- **Payout:** an offer must pay strictly more than the highest standalone payout you have accepted.
- **Rates:** it must also at least match the best pay per minute, per mile and per stop among accepted offers. For example, if your best is $14.20 for 24 minutes, a 30-minute offer needs $17.75.
- **How the floors combine:** each is a floor of its own, compared with the saved rules' total, never added to it.
- **Unknowns:** if an offer doesn't show the minutes, miles or stops a floor needs, it goes to review, never keep or decline.
- **When it learns:** the payout and the bests are learned only while auto-decline and the adaptive minimum are both on. Turning the minimum on never applies highs gathered while it was off. A shared report says when learning was last turned on and off, and when the adaptive minimums were last reset.
- **When an offer counts as accepted:** a wrong lesson would raise your minimums until **Reset** and decline good offers, so when the evidence is unclear nothing is learned, and the history says why. An offer counts when the app sees your Accept tap on a readable offer and Dasher then shows a delivery screen, unless (for a standalone offer) a delivery was already under way when it came, or its countdown had 3 seconds or less left as it went (the tap may have failed as it ran out). Dasher's screens seem to report no finger taps at all, so (your decision) an offer also counts without a seen tap when all of this holds: it is a readable standalone offer the app did not decline (it passed, or was left for your review); the app read Dasher's wait for offers ("Finding offers", the dash's own screen, the dash home, the dash's summary between deliveries with "This dash so far" and "Continue dashing", or the zone screens with "Dash here", "Navigate back to old zone" or "Switch to this zone with peak pay!") after the offer before it and before this one came, so you were waiting, not delivering (after a restart, another offer or a screen it did not recognise since, it does not know, and learns nothing); it closed while its countdown still had more than 3 seconds left, so it did not run out; Dasher never asked "Are you sure you want to decline this offer?" about it, and no Decline of it was seen or requested (on screen or through Dasher's notification); and within a minute Dasher's next settled screen is a delivery or route screen ("Deliver by", "Delivery for", "Pick up by", "Directions", "Arrived at store", "Confirm pickup" and the like, and Dasher's drop-off leg as a report showed it: "Deliver to …", "Leave it at the door", "Hand it to me", "Verify correct order", "Check you have the correct order from pick-up", "Take photo of drop-off location", "Handed order to customer", "Confirm you handed order directly to customer", "Confirm to complete delivery", "Arriving at …", "Arriving soon", "Remember to grab the drinks before delivering the order"), not the wait for offers or the dash's end. A next screen that is neither (one whose words stay the same for 5 seconds), or one showing a delivery and the wait for offers at once, teaches nothing, and its words go to the screens log so a report shows them. Turn-by-turn navigation alone (a speed in mph and a distance, "Turn left", "Exit") is such a screen: it shows on the way to a customer and on the way back to a zone alike. So is Dasher's "End your current dash?": the dash counts as ended only once your "End dash" on it was seen and a screen without the dash followed ("Go back" keeps it on). An empty screen, or one replaced within 5 seconds (such as Dasher's bare page chrome between two screens), is passed over, and so is a screen showing any of an offer's figures (pay, miles, minutes, stops), which is an offer being drawn, except figures the screen explains itself: navigation's distances and times, and the dash summary's amounts ("This offer $9.00"). Add-ons count only with a seen tap, and an offer whose pay was not read never teaches. Each acceptance is learned once. Its route is kept for the delivery and ends when Dasher shows the wait for offers, the dash's end or its home with the Dash button again (with no sign of a delivery on that screen). Once an acceptance is learned, offers must pay more than it (see Payout above), so offers like the ones you used to take may then be declined.
- **What doesn't count:**
  - Add-ons are never judged by these floors and don't set them.
  - An offer with any misread-looking figure (under 5 minutes, under half a mile, or 1 stop) sets no best at all.
  - Short trips pay mostly base pay, so only trips of at least 2 miles set the per-mile best, and only trips of at least 10 minutes the per-minute best. A $7.50 hop of 0.6 miles would otherwise make every 5-mile offer need $62.50.
- **Declines by hand:** tapping Decline yourself on an offer the rules let through means the rules were too lenient. The app notices your Decline when it sees the tap (a Decline control's own label, the control the last offer read found while that offer showed, or a label just below the tapped node, as Dasher's screens put it, when there are a few at most and none of the offer's figures, so a tap on the offer card itself is neither Accept nor Decline), or when Dasher asks "Are you sure you want to decline this offer?" about an offer the app left alone while no decline of the app's own (or through Dasher's notification) is under way. Either one is held, and counts only when Dasher next goes back to the wait for offers, or another offer comes with no other screen between (a seen tap also when Dasher goes back to a delivery that was under way before). It counts nothing when you go back to the offer (even for a moment, unless the wait for offers or the next offer follows at once), when you then tap Accept, when a delivery screen follows (after the question alone, or with none under way before), when Dasher settles on a screen the app does not recognise or shows neither within a minute, or when the dash ends; the history says which. The app never answers that question for you. Only the rule that came closest to catching that offer is raised, just past it (its payout, or its pay per mile, minute or stop), so later offers must beat it. Raising every rule would decline offers like ones you accept. The same guards apply: short trips set no mile or minute floor, and a misread-looking offer teaches nothing. A counted decline teaches only once the next different offer arrives, which shows the dash went on. A decline just before the dash ends or pauses (Dasher's dash-ended screen, or its home with the Dash button) teaches nothing, nor does one of an offer you then accept. Declines the app taps itself, or made while auto-decline or the adaptive minimum is off, never count.
- **Every step is in the history:** under each offer the app left alone, the decision history keeps a "learning" line for each step (you tapped Accept or Decline, Dasher asked to confirm a decline, accepted and learned, not accepted and what came next, not learned and why, what a decline taught or why it was not counted). These lines stay on the phone: automatic reports never carry them, and they never change an offer's count.
- **It only rises:** a lower offer accepted later never lowers anything. What was learned stays through pauses, turning the minimum off and on, clearing the history and updates.
- **Starting over:** only **Reset** clears the payout, every best rate, and what declines taught.

Known failures may decline despite another missing field. One unknown pay is judged by its ceiling, by the user's own rule for one narrow shape (approved in chat): a "+$X" label directly beside an offer's one total "$Y" on a single order (2 stops), which shows up while already on a delivery and may be an add-on. Only the offer's own Decline or Accept button, its countdown or the "Very busy" badge may sit between the two, as on Dasher's screen ("Very busy, +$1, Decline, $5.75"); any other label between them keeps them apart. Pay stays unknown, but the offer as a whole pays at most Y + X, and it is declined when even Y + X falls short of the set rules (the minimum, and per mile, minute and stop with the figures shown). That is the user's choice for this shape, not proof that every reading fails: if the offer really is an add-on, the add-on rules (which judge the combined route and the added pay) might have kept it. The adaptive minimum never counts toward that decline, because it never judges add-ons. Otherwise the offer is left for review ("pay unclear beside a +$ amount"), never kept, and nothing is learned from it. Notifications never use this ceiling. Conflicting, oversized, malformed, negative, ranged, and ambiguous numeric inputs do not become exact facts. Costs use overflow-safe long arithmetic and decimal ceiling for mileage rates.

**Score by area** (off by default; the round toggle with an area-chart icon beside the constellation, its only home; your choice, approved after the trade-offs were explained) judges a standalone offer by the area of its shape instead of by every minimum. Each spoke with a minimum (pay, per mile, per minute, per stop; with the adaptive minimum on, the higher of the set minimum and what the adaptive one asks of this offer on that spoke, in the cents the strict rules ask for it) has a floor `d` in cents for this offer: pay's is the minimum itself, per mile's is `miles × rate`, and so on. The offer's ratio on that spoke is `r = pay ÷ d` (its pay per mile over your per mile, and so on). The offer's points stand at `r` on the spokes in the order they are drawn (pay top-left, per mile top-right, per minute bottom-right, per stop bottom-left) and the minimums' at 1, and the score is `sqrt(area of the offer's polygon ÷ area of the minimums')`. The spokes stand 120° and 60° apart, whose sines are equal, so with all four minimums the score is `sqrt((r_pay·r_mile + r_mile·r_minute + r_minute·r_stop + r_stop·r_pay) ÷ 4)`. With three, two of them stand opposite each other (their triangle has no area) and that pair does not count; with two, the score is `sqrt(r₁·r₂)`; with one, it is `r`. It rises in proportion to pay (twice the pay, twice the score), and does not depend on which offer the chart uses as its example. With your rules ($13, $3.85/mi, $0.41/min, $4.75/stop) $15.00 for 6 mi, 25 min and 2 stops scores 121%: only its per mile falls short ($23.10 needed), and the strict rules would decline it; $4.25 for 2.1 mi, 16 min and 2 stops scores 49%. By area, 100% or more passes and less declines ("score 87% (needs 100%)"), the pay needed being the least that scores 100%; whether an offer reaches 100% is worked out exactly. There is no floor on any single spoke (your decision): only **max stops** stays a hard limit, declining above it whatever the score. An offer with pay unread, or with the miles, minutes or stops a minimum needs unread, is left for review (a missing amount could lift the score); a separate known failure (too many stops, or a score already under 100% while only max stops' stops are unread) still declines. A "+$X" beside a total "$Y" declines only when even Y + X scores under 100% on the set minimums alone (the adaptive minimum never judges add-ons), else it is left for review. Add-ons keep the strict rules. The score is shown for every offer it can be worked out for, in either mode: on its ticket ("Score 121%"), in the history and reports ("score 121%"), and to screen readers.

Add-on offers are not fresh standalone orders. They need explicitly added pay/distance/time/stops or explicitly labeled totals. The flat minimum and stop ceiling apply to the combined route; explicitly added pay is required whenever a per-mile, per-minute, per-stop, or rising-payout rule is enabled, and it must cover `max(added miles × per-mile rate, added minutes × per-minute rate, added stops × per-stop rate)`. Only explicitly added stops count; if they are not shown, the add-on goes to review unless another known failure declines it. Bare numbers do not establish incremental meaning. Old accepted-route travel totals are not subtracted from new totals to invent added miles/time: the route may already be partly completed. A missing active route is not permission to apply the standalone flat minimum to the add-on. Confirmed pickup/completion progress invalidates old travel estimates, and recognized idle screens clear route context. Route context can also be cleared manually.

## The filter button in Dasher

While Dasher fills the screen, a small tab with the mascot's face peeks out from its edge, about half of it tucked past the edge (it is still a full-size touch target). It starts on the left edge a little above the middle. Drag it up or down, or across to the other edge, where you want it: it lands on the nearer edge and stays there, one place for portrait and one for landscape. A drag never counts as a tap. Screen readers get "Move up", "Move down" and "Move to other side". In split screen there is no tab: Offer Filter's own half has the mascot. Blue and awake means auto-decline is on, amber and asleep means paused. A tap pauses or resumes, keeping every rule; with no rule saved yet, it opens Offer Filter. A tap during an automatic decline counts as your touch, so that offer is handed back to you. It needs no extra permission (it is part of the screen-reading service) and leaves when Dasher does.

The tab gets out of the way. Over an offer or its confirmation (or Dasher's "New Delivery!" / "New Order" headline) only a slim bar in its colour shows at the edge, and it takes no touches there: every touch goes to Dasher. During a delivery (an accepted route, or Dasher's delivery or pickup screen with "Deliver by", "Delivery for", "Pick up by", "Complete delivery steps", "Complete pickup steps" or "Directions"), and on any screen it does not recognise while you are dashing, it is the same slim bar until you tap it; then it comes out for a few seconds and tucks away again.

Beside the tab (in split screen, near the top of Dasher's half, under the status bar when that half is on top) a small pill points toward the best offer area: an arrow and "3.6 mi NE · $3.00/mi". North is up, as on Dasher's map while you wait for offers, and the compass point says the same in words. It shows only while Dasher shows that you are waiting for offers ("Finding offers", the dash's own screen, the dash home, the dash's summary between deliveries, or the zone screens) and no delivery is under way; not over Dasher's "End your current dash?". During an offer, a confirmation, a delivery, shopping, or any screen it does not recognise, it stays hidden. Touches pass through it to Dasher.

**Split with Dasher.** The round button with a split phone at the top of the main page (shown while Dasher is installed and not already in the other half) puts Offer Filter in the top half and Dasher in the bottom half, so Dasher stays on screen with its offers in view. Android has no way for an app to split the screen by itself, so Offer Filter asks through its screen reading (the same as Android's own Split screen accessibility shortcut), then opens Dasher in the other half. Many newer phones ignore that request, because split screen now starts from recent apps, and Android's "yes" only means it passed the request on (Pixels from Android 13 then do nothing). So a second and a half later Offer Filter looks again, and if the screen did not split (or Android said no) it opens recent apps for you with words for your phone: on a Pixel, tap Offer Filter's icon above its card, choose **Split screen**, then tap Dasher; on a Samsung, choose **Open in split screen view** and Dasher then opens in the other half by itself; elsewhere, choose split screen from Offer Filter's icon. Once the screen splits within a minute of your tap, Dasher opens in the other half; a split much later opens nothing. Already split with another app in the other half (Dasher's navigation opened Maps there, say), the same button reads **Put Dasher beside** and opens Dasher in the other half. It all happens only when you tap it, and each step is noted in the diagnostic log as a `[split]` line. In split screen, an offer in Dasher's half is read and declined at once even while you are touching Offer Filter's half, as long as Dasher's half is really in view: not under the keyboard (while you type in Offer Filter's half, say), recent apps, a pop-up window or a system window covering half of it or more (the status and navigation bars, or a notification over its edge, don't count). Then Dasher's half is left alone, as when it is off screen, and the log says why, once. Locking the phone does not make Offer Filter forget that Dasher was beside it, so the page comes back as it was, and coming back to the page looks at once whether Dasher is still there. Each screen and alert line in the diagnostic log says where Dasher was, such as `win=split/bottom/ours/48` (split screen, Dasher in the bottom half, Offer Filter's half active, Dasher 48% of the screen's height), `win=full/-/dasher/100` or `win=hidden/-/system/0`, and alert lines also whether the screen was on and locked. Reading Dasher's half runs on the screen reader's own thread, so Offer Filter's half stays responsive while Dasher's map and countdown move. Beside another app, the page stays on screen for a whole dash, so it does less: no tilt sensor, and the steady motion (twinkling, drifting, breathing) draws about ten frames a second instead of every frame (a press or a glide you cause still draws every frame). The page's once-a-second refresh, split or not, asks Android whether Dasher is installed, alerts and installs are allowed and location is permitted at most every 30 seconds, and again at once when the page comes back from elsewhere; where the phone is, for the map's dot, every 5 seconds while the map shows.

## Offer areas

On from the start (the homepage's ground is the map), and nothing is kept until approximate location is allowed; **Offer map** in Settings turns it off. While on, each new standalone offer with a known pay is added to the square of about 2 km the phone was in when it appeared.

- **Location.** Only approximate location is asked for, never precise. The position is the newest fix the phone already has (no GPS is switched on for this), used only if it is under ten minutes old, and rounded to its square before it is kept.
- **Counting.** An offer seen from its notification and then on screen counts once. Add-ons and offers without a pay are left out. An offer with no fresh location is only counted as "without a location". If that happens, Settings has a **Fix** row asking for location all the time, since Android may share location only while Offer Filter is in front.
- **Ranking.** A square is ranked by pooled pay per mile (all pay over all miles, so one short trip cannot dominate) once three offers with miles came in there.
- **Privacy.** A square is where you were when an offer came in, not where its pickup is. Squares are not in reports (the diagnostic report says only how many), and the map is drawn without map tiles. Neighbourhood names come from the phone's own place lookup (Android's geocoder, which on most phones asks Google's servers): only positions rounded to about half a kilometre are asked about, each once, and the names are kept on the phone; nothing about offers goes with them. **Open in Maps** hands one square's center to your maps app only when you tap it. **Clear history** removes them all, with the decisions and the captured text (one confirm lists all three).

## Decision history and diagnostics

Every offer the app evaluates is recorded on the phone, always on and bounded to the latest 200: time, source (screen or notification), the pay/miles/minutes/stops read, the pay the rules required, the offer's score by area where it can be worked out (in either mode), the result and reason, what the app did (for example "Decline tapped", "Notification hidden; order NOT declined", "Passing alert rang"), and whether auto-decline was paused. It also keeps only the lines that carried a figure or a pay label (such as `$7.90`, `Guaranteed (incl. tips)`, `2 stops (7.2 mi) • 21 min`), masked like all kept screen text (below), so a misread can be spotted without names or addresses. One offer is one line. Dasher's notification of an offer is folded, without its lines, under the screen's line for it ("notification 14 s earlier | REVIEW | …", and on the ticket) when that is the readable screen offer next to it: the first one read after it, within what that offer's countdown allows (30 seconds when none shows), or, while Dasher is on screen, the one read at most 12 seconds before it. A notification that says add-on never folds into a standalone offer, figures that differ never fold, and a known failure the notification path acted on keeps its own line. Two notifications are two lines, with one exception: when the screen reads an offer again (say you left Dasher, its notification came and was announced as a possible next offer, and you came back to the same offer), every notification recorded since that offer's line, within what its countdown allows, was that offer's. The line keeps the first of them, and the rest leave the history and the counts. The first time the history is read after updating, the stored history is folded the same way, once, and the folded notifications are taken out of the all-time totals; double counts older than the kept 200 lines stay in the totals. The skyline on the main page shows the latest 14 as buildings (pay) against ropes (needed pay), each with a ✓/✕/? flag. A building ending below its rope was declined by the rules as written; tap it to see its ticket with what was read and what the app did. Clear history removes it.

### Diagnostics after each dash

**Share diagnostics after each dash** (Settings, off by default) sends that same report without a tap. It can be turned on only while GitHub is connected and **Send problem reports** is on; turning either off (or turning reports off, or disconnecting GitHub, or a connection that ends by itself) turns it off and discards anything not yet sent, as turning the switch off does. Connecting again never turns it back on.

With it on, a dash runs from its first offer (on screen or in Dasher's notification) to its end: Dasher showing the dash ended (its summary, or the "Dash now" home; a pause is not an end), Dasher's **End dash** screen when nothing else of the dash shows, or 30 minutes with no offer after the last one. Then the report is filed as one issue in this private repository, titled `[diagnostics] Offer Filter <version> 2026-09-30 18:02–21:47` with the label `diagnostics` (GitHub may drop a label the connection may not set, and one it refuses is left off; the title always marks them), whole (never cut at 60,000 characters as a shared report is) and split into the issue body and comments of at most 60,000 characters each. At most one issue per dash and six a day. It goes through the GitHub connection's own token only (never a pasted one), only to this repository's issues, and waits in the same queue as problem reports: offline it is retried with backoff, and once the issue exists its number is kept, so a retry sends only the comments still owed. The token is never logged or included. The fixer never acts on `[diagnostics]` issues; they are for reading, by you or by a Claude session you give this repository.

## Automatic problem reports and the fixer

Problem reports go only through the GitHub connection. Once GitHub is connected for updates, Settings shows **Send problem reports** (off by default): turning it on is the opt-in, and the "Offer Filter Updates" GitHub App (it keeps its old name) then also needs **Issues: Read and write**. Adding the permission to the app is only half of it: the installation must accept it too (github.com → Settings → Applications → Installed GitHub Apps → **Configure** next to the app → accept the new permissions; GitHub also emails a request to review them). Until then GitHub answers 403, the status line shows GitHub's own words and what to do, and reports wait; each time Offer Filter opens, it tries them again with a freshly renewed token. Connecting GitHub alone never turns reports on. Turning that switch off, or disconnecting GitHub, stops reports and discards anything not yet sent. Older versions also took a pasted report token: updating removes it from the phone, with any problem report that was waiting to go with it (a report token is never used again), and leaves **Send problem reports** as it was. With reports on:

- An offer screen the rules could not judge (pay, miles, time or stops not readable) is reported once per reading gap per app version.
- A declined offer, or its confirmation, still on screen 5 seconds after the Decline tap is reported once per offer. Dasher keeps ringing while it shows.
- A screen-read or notification-handler crash is reported once per error site per version.
- **Report this offer** appears when a history row or chart column is opened. It asks what went wrong (optional) and files the offer with what was read.

At most 10 automatic and 20 user reports go out a day, by the phone's clock.

Each report is an issue titled `[offer-report] …`, holding the rules, the decision, the screen lines and recent decisions as JSON. Before a report leaves the phone, its screen lines are masked as the phone keeps them (names, addresses, phone numbers, emails and instructions become `[name]`, `[address]`, …), and then every other word that isn't offer vocabulary (pay, guaranteed, stops, mi, accept, decline…) is masked to its shape. "Order for Jane D. at Chick-fil-A $7.90" becomes "Order for [name] at Xxxxx-xxx-A $7.90", so store names, customer names and streets never leave. Runs of four or more digits (ZIP codes, house and phone numbers) become `#`, and so do error messages. Offer figures stay, so a misread can be reproduced. The issue is read by Claude in the fixer workflow, so a report goes to Anthropic as well as to GitHub.

Reports queue on the phone and send when any network is available. An outage or rate limit is retried later with backoff. A report GitHub refuses for the connection's sake (a missing permission, say) is kept and tried again each time the app opens. Only a report GitHub refuses as invalid is dropped.

Opening such an issue starts `.github/workflows/offer-report-fixer.yml` (only `[offer-report]` titles count; `[diagnostics]` issues never start a fix). It is event-driven, never scheduled. Each run handles every report still waiting, oldest first, one at a time, and closes exact resends as duplicates. Each report goes through `offer-report-fix-one.yml`, in three jobs with separate permissions:

1. **Diagnose** (read-only token, no build caches). Claude follows `tools/fixer/PLAYBOOK.md`: explain a decision the rules made, or reproduce a misread or crash with a failing test, fix it, bump the version and commit. The commit leaves the job only as a git bundle. A session that runs out of turns or time ships nothing.
2. **Gate** (read-only, fresh machine). The commit is applied on top of `main`, and `tools/fixer/gate.sh` runs as it was on `main` before the fix. It requires:
   - exactly one commit, touching only app code, tests, the version lines and notes (never the updater, and moving a protected file counts);
   - changed tests that compile against the old code and fail there;
   - no skipped or removed tests;
   - the full suite and lint passing;
   - an APK that packages.
3. **Ship** (the only job that can write, and it runs no code from the fix):
   - pushes exactly the gated commit to `main`, where Render builds, signs and publishes as usual;
   - waits for the live feed and runs `tools/verify_channel.py`;
   - comments on the issue and closes it (shipped, or explained). Anything else stays open, labeled `fixer:needs-human`, with the reason.

The fixer is opt-in until its Android SDK setup is repaired (its runs failed there and emailed the owner each time): it runs only while the repository variable `OFFER_FIXER_ENABLED` is `true`. Unset, or anything else, skips every run.

Screen text is captured automatically: what the screen reader and the notification path saw and did, including Dasher's screen text (offers, and its other screens such as a shopping list), goes into two small rolling logs on the phone, never older than a day: one for offers, decisions and status, one for Dasher's other screens, so a few minutes of shopping never push the offers out. Each keeps about what one report can carry, and a screen whose only change is a ticking number is kept at most once a minute. Turn-by-turn navigation (a speed in mph and a distance) changes its words at every turn, so it is kept at most once a minute whatever it says, on a budget of its own: it never holds back another screen, and when the screens log (or a report's share of it) is full, navigation and screens older than 30 minutes go first, so navigation never pushes another screen of the last 30 minutes out (the pickup leg after an Accept stays). There is no switch to remember. Every line is masked before it is written (see Reports and privacy above). It leaves the phone only inside a report you share yourself, or in the diagnostics after each dash once you turn that on; automatic problem reports never include it (they carry only masked offer labels). Masking is by pattern, so review a report before sharing it anywhere else. Reports include the Android version and the phone's maker under the title ("Android 15 (API 35), Google"; never in an automatic problem report), every saved rule (including the rising-payout baseline, and when learning was last on and the adaptive minimums last reset), notification-access and service readiness, the decision history (with its learning lines), updater status, the latest advertised version and which feed advertised it, last check timestamps, how many automatic update checks found the same result or were too soon to start since the last logged update line (by what started them), the GitHub connection's state and when and why it last ended, the latest copy of each state logged once per change ("Latest states", at most a day old), the newest 14,000 characters of the offers log and 10,000 of the screens log (navigation going first, as above), each in whole lines. Arbitrary notification-extra values are not interpreted as numeric evidence or dumped to logs. Some lines are states rather than events, so they are written only when they change (and at least once a day): what an automatic update check found, and DoorDash's alert-channel settings and extra-key names, per channel. A failed update check, a check you start yourself and every install step are always written. Around offers, the screens log also keeps Dasher's taps (whose they were, what the tapped node and those around it say, and what the app made of it; away from offers only the shape, now and then) and up to three of Dasher's screens in the 30 seconds after an offer the app left alone has left. **Clear history** removes the decisions, the captured text, the kept states and the offer areas.

## Build and release

The private source repository feeds the existing Render static build. `render-build.sh` installs the SDK/JDK as needed, verifies the current public channel using the production Java downloader, runs the JUnit and Robolectric suite, builds/signs the APK with the existing Render-held key, checks embedded package/version, and publishes only APK, feed, receipt and install-page assets.

Update checks are always automatic: Settings has no switch for them (an "off" an older version kept is turned back on, once, and logged). They are spaced: opening the app, the retry job and a tap on **Updates** in Settings check at once (after the one-minute cooldown that follows a check, or the backoff after a failure); coming back to the app, a resize or day-and-night recreation, a service reconnecting and the periodic job wait five minutes after the last attempt. While you are dashing, an update an automatic check found waits ("Update ready: installs after your dash", looked at again every five minutes): installing closes Offer Filter, and with it its half of a split screen beside Dasher. A tap on **Updates** still installs it mid-dash, except while Dasher is on screen.

`app/build.gradle` is the version source of truth. A changed source commit cannot reuse the live version code. A deliberate same-source redeploy reuses the already published APK/feed bytes after checking them, preventing mutable content under one version. `verification.json` reports test totals and the exact live version reached by the production-transport probe. The app trusts two release origins, each with one exact feed and one exact APK address, and checks every redirect hop against them: the Render host, and this repository's `release/` folder on `main`, read through the GitHub API. Whichever advertises the higher version code is used (a tie goes to Render), and one being unreachable does not stop the other. The retired GitHub feed is neither trusted by the app nor published to by any script in this repository. The manual-tests workflow and the offer-report fixer never sign or publish: the fixer only pushes a gated source commit to `main`, and Render signs with the existing key.

When Render cannot build (for example when the workspace is out of build minutes), `tools/sign-local.sh` builds and signs the same release in a Claude session. The same cloud key reaches the session only through the environment variables `OFFER_FILTER_KEYSTORE_B64` and `OFFER_FILTER_SIGNING_PASSWORD`, which the user sets in the environment settings. The script refuses any other certificate, runs the tests, and leaves `dist/OfferFilter-<version>.apk`, which installs by hand over the current app with settings kept.

To ship that APK to phones without Render, commit the source and run `tools/publish-repo-feed.py`. It refuses an uncommitted source, any other signer, a package or embedded version that disagrees with `app/build.gradle`, and a version code not above the one already in `release/`, and checks the feed with the app's own policy code. It then writes `release/OfferFilter.apk` and `release/latest.json`, naming the source commit. Commit `release/` on its own and push both commits to `main`. Nothing is signed on GitHub, and no workflow or paid service is involved.

### Updates from the repository (Connect GitHub)

The repository is private, so a phone reads `release/` with its own GitHub sign-in:

1. **Once, on GitHub:** create a GitHub App owned by your account (Settings → Developer settings → GitHub Apps). Tick **Enable Device Flow**, turn the webhook off, and give it only **Repository permissions → Contents: Read-only**. Install it on this repository only, and put its **Client ID** (public, not a secret) in `GitHubConnect.CLIENT_ID`. Builds without one hide the feature.
2. **On the phone:** Settings → **Connect GitHub**. The app asks GitHub for a short code, copies it, and opens github.com/login/device. Paste the code and approve.

The token can only read this repository's files, is limited to this repository, and refreshes itself with the client ID alone (no client secret, no server). It is kept in the app's private storage and sent only to GitHub. Tapping the connected GitHub row asks, then disconnects and forgets it. A refused refresh forgets it too and says to connect again, and so does a connection whose renewal ran out (GitHub's limit); either way reports sent through the connection stop and unsent ones are discarded, as with Disconnect, and connecting again never turns them back on (Connect GitHub forgets any connection still stored, also one that ran out before the app noticed, as Disconnect does, and a new connection starts with reports through it off). One renewal runs at a time: anything else that needs the token meanwhile waits and uses what it stored, and nothing waits for GitHub while holding the stored connection, so Disconnect never freezes Settings. Why the connection last ended (disconnected in Settings, refused, ran out) is logged and kept for a shared report, never the token, the account name or a code.

The user-visible name is `AppName.NAME`, with one twin in `res/values/strings.xml` (the `app` entity, for what Android shows from the manifest): a rename changes those two lines, and `AppNameTest` fails while they differ or anything else spells the name out. After editing TERMS.md, PRIVACY.md or LICENSE, run `python3 tools/legal_texts.py` so the app's copy matches.

Run `./gradlew --no-daemon testDebugUnitTest`, then `./build-local.sh` with the existing signing environment. The network probe is `python3 tools/verify_channel.py`. The app has minSdk 26 and no core-library desugaring, so Java APIs newer than Android 8 (for example `List.of`) crash on older phones even though the JVM-hosted tests pass; `./gradlew lintDebug` reports these as `NewApi`. Local pure-Java checks are not handset installation tests; Robolectric adapter tests are not a physical phone or the real DoorDash client.

## Current limitations

No official DoorDash API integration, hidden-background UI access, global audio muting, or device-level vibration suppression is implemented. Notification identifiers are not guaranteed unique order IDs. Acceptance is seen from the user's Accept tap (which Dasher may not report) or, without it, from an offer closing with time left into a delivery screen Dasher's words show, after the app read Dasher's wait for offers before that offer; a delivery screen worded in a way the app does not know, an offer that came during a delivery or with no wait for offers read before it (after a restart, say), or one accepted while Dasher was not on screen teaches nothing and may leave route context unknown. Whether Dasher reports finger taps, and its wording after an Accept, are unverified on a real phone until a report shows them. Android may defer periodic/one-shot work or require an update-installation confirmation. Changing these limits needs additional evidence or capabilities, not more optimistic labels in the UI.

See `AUDIT.md` for the adversarial findings and test boundaries.
