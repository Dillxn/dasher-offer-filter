# 0.4.73 acceptance and validation

Status: reconstructed candidate; fresh aggregate validation and signed publication pending. This is not a claim that the earlier workspace's tested tree has been restored byte-for-byte. Draft recovery commits preserve each component on a separate branch; they are not update-feed releases.

## Feature acceptance

- **One simple selectivity control:** native 1–200% one-point slider, accessible current value and explicit lower-minimum/more-offer versus higher-minimum/more-money-goal labels. Compact windows open the control from the existing chip; roomy windows can show it inline. Strict/area mode remains a separate deliberate choice. Higher pay target is not a promise of more earnings.
- **Existing minimums:** saved and learned floors, exact scoring, per-item learning, manual takeover and migrations are preserved. A manual scale change disables the optional optimizer before saving the new percentage.
- **Local costs:** explicitly entered per-mile cost, blank unknown and explicit zero distinct. An optional calculator uses the driver's own fuel price, observed MPG and wear allowance; it does not query a price provider or fabricate a profitable default.
- **Acceptance-rate history:** bounded, dated, manually entered reported rates, at most 200 over 30 days. This implements inspectable manual history, not automatic platform AR capture. The date may select a sufficiently supported cohort; numeric AR is not a causal dispatch multiplier.
- **Observed offer frequency:** the existing prospectively monitored numeric arrival/wait history (at most 200/24h) supplies matching frequency and model inputs. Hidden/locked/unknown/delivery time and old decision timestamp gaps are not invented waiting.
- **Optional automatic adjustment:** off by default, separate risk confirmation, explicit costs, selected bounds, at most 5 points and no more often than 15 real minutes plus fresh evidence. Requires 20 readable arrivals, 5 matches, 30 monitored minutes and a gain of at least 5% and $1/hour corroborated in both chronological halves. Only ordinary, complete, fresh, visible/unlocked stable waiting reads can initiate it; final rule/config/history/window generations must still match. No tap, lock, foreground or identity guard is weakened.
- **Local estimates:** modeled net offer-cycle rate, not actual completed earnings, an official dispatch model, proof of AR causality or an established long-run earnings optimum. Return mileage, unobserved time, route overruns and omitted costs remain unknown. These limits are explicit in the app.
- **Platform coverage:** minimum Android 8/API 26 retained. Required simulated adapters run 26/35/36. Optional API 27 runtime could not be downloaded in the earlier environment (403); no alternative host was used. The 8.1 slider workaround has official-source review and 26/28 framework corroboration, but API 27 runtime is not claimed passed. Optional source requires both testApi27 and allSdks.

## Earlier shared-thread bugs and remaining device evidence

This candidate builds on published 0.4.72 and preserves its parser, updater, Peek, decline/error/map recovery, split-window, touch, notification and sound protections and regressions. It does not infer that every historical handset report is repaired from unit tests. Existing bounded failed-decline recovery still requires its exact fresh error and original identity/deadline; hidden/locked notifications remain conservative, and hiding a card is not declining an order.

Reported 0.4.72 handset diagnostics provide some successful decline terminal sequences. They do not establish that every decline hang, map mismatch or audible native alert is resolved. A locked unknown-pay REVIEW with an audible-request flag proves a request was recorded, not the sound heard or successful silencing. Historical AR figures are not a current rate or causal evidence. Physical installation of this candidate, real DoorDash sound/haptics, split-screen/map behavior and realized earnings require separate field validation.
