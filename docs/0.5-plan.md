## Non-negotiable invariants (from AGENTS.md — read it)
- Unknown is REVIEW, never KEEP or DECLINE. A separate KNOWN failure may still decline. Never infer pay, travel (miles/minutes) or add-on increments. "Deliver by 7:45 PM" is a deadline, never minutes.
- Preserve the immediate first decline attempt on a readable, failing foreground offer (no added delay before the click; record history AFTER the click).
- Never open/foreground Dasher automatically. The tile and UI never launch Dasher except when the user taps a card/row that explicitly says "Open Dasher".
- A click or PendingIntent send = "requested", never "declined". Hiding a notification is NOT declining. UI copy must say "Decline requested", "Notification hidden — order NOT declined", "Accept observed". Never "Declined", "Earned", "Saved $X".
- No repeated rings: one passing bell per notification incarnation; replay/reconnect/update never ring. Never remove an original passing/unknown notification merely because a replacement was attempted.
- Data stays on-device. Network only for updates. No new network calls, no analytics, no export except explicit user-initiated share sheets (diagnostics already exists).
- Framework-only runtime: Java 17 source, Android framework APIs only (minSdk 26, targetSdk 35, compileSdk 36). No AndroidX/libraries. The release APK is built by build-local.sh (aapt2 + javac + d8 against android.jar).
- NEVER generate signing keys, never sign APKs, never touch signing config, render-build.sh key logic, or publish anything. Never push/commit (the orchestrator commits once at the end).
- Do not create git branches or worktrees. Do not run `git stash`, `git checkout -- <file>` on files you don't own, or anything that discards other agents' work.

## A. Parser & safety fixes (money-losing bugs reproduced by research probes)
A1. Pay label before/after: DoorDash's redesigned card puts the amount BEFORE its label, in separate nodes: ["$28.24","Guaranteed","Includes a $15.00 Flash offer boost", ...]. Today parsePay looks only AHEAD from a money-less "Guaranteed"/"Total pay" line and takes $15.00 (the boost) -> wrong DECLINE. Fix: when a pay label line has no money, look at the immediately preceding line AND the next line; a line that is exactly a single money token adjacent to the label is a candidate; if the previous line is a standalone money token it wins over a next line that is a component line. Component/breakdown lines ("includes", "boost", "peak pay", "bonus", "tip", "promotion", "incl.") are never pay candidates in the unlabeled fallback either, except when they are the label line itself like "$7.50 Guaranteed (incl. tips)". If still ambiguous -> null (REVIEW). Add regressions for: flash split nodes, flash merged node, "(incl. tips)" split/merged, original card "Includes DoorDash pay and customer tip".
A2. Earn by Time / hourly cards: "$15/active hr + tips", split ["$15","/active hr","+ tips"], "From when you accept to when you complete this offer". Any rate context ("/active hr", "per active hour", "/hr", "an hour", "hourly", "/ hr", next line starting with "/" or "per ") makes that money a rate, never pay. If an Earn-by-Time marker ("active hr", "active hour", "from when you accept to when you complete") appears anywhere on the screen/notification, the whole offer is "hourly mode": pay = null AND the decision must be REVIEW with reason "Earn by Time offer — auto-decline disabled (DoorDash ends the dash after more than one decline per hour)" even if another rule would fail. Expose as OfferSnapshot/parse metadata or a separate OfferParser.isHourlyMode(labels) used by OfferRule entry points.
A3. "Add to route" is the add-on ACCEPT control (with optional countdown "Add to route 77", "Add to route (77)"). OfferControls.isButton(label,"accept") must recognize it (and "Accept offer"/"Accept order" as today). Consequences to verify with tests: add-on cards are no longer mistaken for decline confirmations; isAcceptClick records "Add to route" taps; add-on evaluation path actually runs on screen.
A4. Harden DeclineConfirmation.isSurface: a surface that shows offer evidence (a money token or a mileage token) and a Decline control but no recognized accept label and no prompt text must NOT be treated as a confirmation (an unrecognized accept label must fail safe to "not a confirmation"). Keep: prompt text ("are you sure", "decline this", acceptance-rate text) or Decline + Cancel/Go back still qualify. Existing DeclineConfirmationTest cases must keep passing (adjust only if a case encoded the unsafe behavior; explain in the test).
A5. NotificationOffer.isLikelyOffer: recognize "flash offer" (e.g. title "$28.24 Flash offer available", body "3.2mi offer from Mr. Pollo. ... Tap to view offer details."). Merchant extraction also supports "offer from <store>." (stop at sentence end) in addition to "go to <store>".
A6. Plus every CONFIRMED audit finding listed in section H (added by the orchestrator).

## B. Rules
B1. FilterSettings (immutable): keep the existing 6-arg and 8-arg constructors (tests use them). Add a full constructor and copy helpers (withEnabled(boolean), withLastAccepted(...), etc.). Every place that rebuilds settings (MainActivity.pause, tile, save) must use copy helpers so no field is dropped.
   New fields: perHourCents (int), maxMilesHundredths (int; 0 disables), avoidStores (unmodifiable List<String>, normalized via StoreMatcher.normalizeTerm, <=50 terms, each 2..60 chars with >=2 alphanumerics), lastAcceptedAt (long wall ms; 0 = unknown), maxDeclinesPerHour (int; 0 disables; opt-in runaway guard).
   hasAnyRule(): any numeric rule, maxStops, maxMiles, risingOffers, or non-empty avoidStores. hasPayRule(): flat/mile/minute/hour/extraStop/rising.
B2. FilterStore: keys "hour", "max_miles", "avoid_stores" (newline-joined), "last_accepted_at", "max_declines_hour". save() writes "minute" and "hour" both. Migration on load: no "hour" key and "minute" > 0 -> perHour = minute*60, perMinute = 0 (exact). Round-trip of settings built with the legacy constructors must be preserved. recordAccepted(context, cents) also stores the timestamp.
B3. OfferRule time rule: byTime = max(minutes*perMinuteCents, ceil(minutes*perHourCents/60)) using long math. Either rate > 0 and minutes unknown -> missing.
B4. Max miles: known miles > max -> DECLINE "7.2 mi exceeds your 6.0 mi maximum" (BigDecimal compare; equal passes). Enabled and unknown -> missing. For ADD-ONS: apply max miles only to an explicitly displayed route total (AddOnOffer must track whether combined miles came from an explicit "Total … mi"/"… mi total" label). A derived active+delta sum never triggers a max-miles DECLINE; it counts as missing.
B5. Avoid stores (StoreMatcher, pure): normalize NFKC -> NFD strip combining marks -> lowercase(Locale.US) -> drop apostrophes ' ’ ‘ ` ´ and periods -> "&" -> " and " -> collapse every run of non-alphanumerics to one space -> trim. Match a term only as a whole normalized label OR a whole-phrase at a word boundary inside the label: (" "+label+" ").contains(" "+term+" "). Standalone screens: match against visible non-button labels. Notifications: match against the extracted merchant (and the notification labels). ADD-ON screens: do NOT match screen labels (the current route's store can appear); only a notification-derived merchant may apply. A match is a separate known failure: DECLINE "avoided store: <term>" even with unknown pay (subject to A2 hourly-mode REVIEW).
   Store rules NEVER create KEEP: if no non-store rule is enabled, a non-matching offer is REVIEW ("no pay rule set"), never "meets enabled rules" (otherwise every merchant-only notification would ring the passing bell).
B6. Rising baseline expiry: the baseline applies only if lastAcceptedAt is within the last 8 hours (and not in the future by more than 5 min). A legacy baseline with no timestamp does not apply (loosening only). UI shows the baseline value and "accepted 7:12 PM" or "expired".
B7. Runaway guard (opt-in, 0 = off): if maxDeclinesPerHour > 0 and the number of decline REQUESTS (screen clicks + notification decline actions + hides count too) in the trailing 60 minutes has reached the limit, a would-be DECLINE becomes REVIEW "decline limit reached (N per hour)" — no click, no hide. It only ever reduces automation. Counting lives in a small pure class (DeclineBudget) fed from history/in-memory timestamps; the first decline attempt while under budget stays immediate.
B8. OfferRule.Decision gains an explanation: List<String> breakdown (e.g. "Flat minimum $7.00", "7.2 mi × $1.50/mi = $10.80", "21 min at $25.00/hr = $8.75", "+ $2.00 for 1 extra stop", "Must beat last accepted $30.00", "Max 10.0 mi: 7.2 mi OK") and a short machine reason code (PAY_MISSING, MILES_MISSING, MINUTES_MISSING, STOPS_MISSING, ADDON_AMBIGUOUS, FLOOR, PER_MILE, PER_HOUR, EXTRA_STOPS, MAX_STOPS, MAX_MILES, AVOIDED_STORE, RISING, HOURLY_MODE, DECLINE_LIMIT, NO_PAY_RULE, MEETS). Existing summary() output format for KEEP/DECLINE lines should remain recognizable (tests assert on some strings — keep them passing).
B9. New entry points taking the visible labels + context: OfferRule.evaluate(OfferSnapshot, List<String> labels, FilterSettings, EvaluationContext) (context: store merchant if known, isAddOn, declineBudget state). Keep old signatures working (delegating) so existing tests remain valid.

## C. Metrics (pure OfferMetrics)

### H3. Verifier-refined fixes (preferred designs; they preserve existing tests)

#### pay-label-lookahead-adopts-next-line (core, high)
In OfferParser.parsePay, replace the one-way lookahead. A pay label with no money of its own may take its amount only from a neighbouring line that is nothing but one amount. The previous line counts too, so a caption under the amount works. If both neighbours are bare amounts and they differ, pay stays unknown (REVIEW):

```java
private static final Pattern BARE_MONEY = Pattern.compile("\\$\\s*(\\d{1,4}(?:[.,]\\d{1,2})?)");
private static Integer bareAmount(String line) { Matcher m = BARE_MONEY.matcher(line); return m.matches() ? cents(m.group(1)) : null; }
...
boolean ambiguous = false;
...
if (payLabel && !MONEY.matcher(line).find()) {
    Integer before = i > 0 ? bareAmount(lines.get(i - 1)) : null;
    Integer after = i + 1 < lines.size() ? bareAmount(lines.get(i + 1)) : null;
    if (before != null && after != null && !before.equals(after)) ambiguous = true;
    else if (before != null) labeled.add(before);
    else if (after != null) labeled.add(after);
}
...
if (ambiguous) return null;   // before the labeled/all resolution
```

Lines are already NFKC-normalized and trimmed, so `matches()` is strict. Rate lines ($/mi, /hr), "+$" deltas, and lines naming Peak Pay, tips or earnings can never be adopted as labeled pay. They still fall into `all`, where a conflict gives null, so the result is REVIEW and never a wrong exact value.

A more conservative variant: don't adopt `before` at all, only skip the lookahead when `before != null`. The caption case then resolves through `all` and gives REVIEW when a Peak Pay line is present.

## Rejected ideas (do not build)

- Auto-accepting offers, whether by tapping Accept or firing the notification's Accept action. It commits the dasher's time irreversibly, turns any parse error into a real loss, and goes beyond the app's request-decline authority.
- Automatically opening or foregrounding Dasher, or waking/unlocking the screen, to read a merchant-only background offer. AGENTS.md forbids it, and it also exposes filtered offers and grabs focus while driving.
- Auto-declining unknown offers 'because they'll expire anyway', or declining REVIEW offers when the timer is about to run out. Unknown must stay REVIEW.
- Inferring pay, miles or time from merchant history ('Chick-fil-A usually pays $7'), GPS or map distance to the store, 'Deliver by' times, old accepted-route totals, arbitrary notification extras, or 'hidden tip' tricks.
- Uploading or syncing offer history or rules: cloud backup, analytics or crash SDKs, crowd-sourced zone or store data, remote rule pushes or remote kill switches. Data stays on-device, the network is for updates only, and no runtime libraries are allowed.
- Cancelling DoorDash's original passing or unknown notification to 'replace' it with ours, or dismissing unknown offers to reduce noise.
- Calling a click, a PendingIntent send or a hidden notification 'Declined'. The same goes for 'Saved you $X' badges or acceptance-rate estimates shown as fact.
- Global audio control (muting the notification stream, switching the ringer to silent, toggling DND) to quiet Dasher. It also silences navigation, calls and the app's own passing bell, and it isn't real control over Dasher's audio.
- Extra automation inside Dasher: GLOBAL_ACTION_BACK to dismiss offers, swipes or scrolls to reveal hidden fields, answering unknown decline-reason pickers, or retrying declines without limit.
- Automatically tuning thresholds from history, so learned rules silently change what gets declined. Suggestions only, and the user must press Save.
- A countdown on review cards suggesting DoorDash's offer timer. The real timer is unknown; the 90 s is only the app's own evidence window.
- FLAG_INSISTENT or repeating bells until acknowledged. This breaks the 'no repeated rings' invariant.
- AndroidX, Material Components, Compose or any runtime library for a nicer UI. The release APK is built with aapt2+javac+d8 against android.jar only.
- DoorDash branding (red #FF3008, logo, look-alike name or styling) in the icon or UI. That is impersonation and a trademark risk.
- Exported intents or broadcasts that resume auto-decline or edit rules (e.g. for Tasker), because any app could then switch on declines. Only pause may be triggered from outside.
- Screen OCR through MediaProjection to read offers Accessibility can't see. It needs an OCR library, captures everything on screen, and harms privacy.
- A faster GitHub release feed, a second signing path, or in-app key generation. AGENTS.md makes the Render feed and the existing cloud signer the only release path.
